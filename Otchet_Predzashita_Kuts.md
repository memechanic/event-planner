# 2. Проектирование веб-приложения

## 2.1. Архитектура приложения

Приложение построено по классической двухзвенной архитектуре «клиент — сервер» с разделением на два независимых слоя. Серверная часть реализует REST API и управляет хранилищем данных, клиентская — формирует пользовательский интерфейс и взаимодействует с сервером исключительно через HTTP-запросы. Такое разделение фиксирует явный контракт между частями приложения, допускает независимое масштабирование и тестирование каждого слоя.

Серверная часть основана на фреймворке Django 5.2 с расширением Django REST Framework (DRF). Django предоставляет ORM, механизм миграций, маршрутизатор URL и административный интерфейс. DRF добавляет поверх Django набор инструментов для построения REST API: обобщённые классы представлений, сериализаторы, переговоры о формате ответа и встроенный Browsable API для ручного тестирования эндпоинтов. В качестве СУБД на этапе разработки применяется SQLite — встроенная в Python файловая база данных. Переключение на PostgreSQL предусмотрено: в файле `requirements.txt` уже присутствует пакет `psycopg2-binary`, а параметры подключения вынесены в закомментированный блок с поддержкой `dj-database-url` и переменных окружения через `python-dotenv`.

Клиентская часть построена на Vue 3 с использованием Composition API и `<script setup>`. Приложение является одностраничным (SPA): навигация между разделами выполняется без перезагрузки страницы через Vue Router, а данные хранятся в реактивных хранилищах Pinia. В качестве инструмента сборки используется Vite 7.3, который запускает dev-сервер практически мгновенно, раздавая исходные модули браузеру напрямую через нативные ES-модули. Визуальная часть полностью реализована на Tailwind CSS — утилитарном фреймворке, где стили задаются набором классов прямо в HTML-шаблонах, что исключает написание отдельных CSS-файлов.

Взаимодействие клиента с сервером в процессе разработки осуществляется через механизм proxy Vite: запросы браузера на путь `/api/*` прозрачно перенаправляются на адрес `http://127.0.0.1:8000`, где запущен Django. Это решение устраняет проблему CORS без необходимости настраивать заголовки на стороне сервера и позволяет обоим процессам работать на разных портах — 5173 (Vite) и 8000 (Django) — как единое приложение с точки зрения браузера.

## 2.2. Проектирование базы данных

Схема базы данных спроектирована вокруг шести сущностей: `EventUser`, `Event`, `DateOption`, `Participant`, `Vote`, `Message`. Центральной сущностью является `Event`, к которой через внешние ключи привязаны все остальные объекты. Такая структура отражает предметную область: мероприятие — главный агрегирующий объект, вокруг которого группируются даты для голосования, участники, голоса и сообщения чата.

Принципиальным решением при проектировании стало применение UUID (Universally Unique Identifier) в качестве первичных ключей для сущностей `EventUser`, `Event` и `Participant`. UUID генерируется Django-функцией `uuid.uuid4()` на стороне сервера и представляет собой 128-битный идентификатор. В отличие от автоинкрементных целочисленных ключей, UUID непредсказуем: зная адрес одного мероприятия, невозможно подобрать адрес другого перебором. Это особенно важно для URL пригласительных ссылок вида `/event/<uuid>`.

Сущность **EventUser** хранит данные пользователя: `id` (UUID, первичный ключ), `username` (строка до 100 символов, уникальное), `email` (строка, уникальное). Намеренно не используется встроенная в Django модель пользователя `AbstractUser`, поскольку приложение не предусматривает механизма паролей. Идентификация пользователя осуществляется по паре «имя + email», что упрощает порог входа для участников мероприятий.

Сущность **Event** хранит мероприятие: `id` (UUID, PK), `event_user` (FK → EventUser, CASCADE), `title`, `description`, `created_at`. Связь с `EventUser` через CASCADE означает, что удаление пользователя автоматически удаляет все его мероприятия. Сущность **DateOption** представляет вариант даты для голосования: `id` (автоинкремент), `event` (FK → Event, CASCADE), `date` (DateTimeField). Каждое мероприятие имеет один или несколько вариантов.

Сущность **Participant** связывает пользователя с мероприятием: `id` (UUID, PK), `event` (FK → Event, CASCADE), `event_user` (FK → EventUser, CASCADE). Ограничение `unique_together = ('event', 'event_user')` на уровне базы данных гарантирует, что один пользователь не может быть добавлен в одно мероприятие дважды. Сущность **Vote** хранит голос участника: `participant` (FK → Participant), `date_option` (FK → DateOption), `voted_at`. Ограничение `unique_together = ('participant', 'date_option')` запрещает повторное голосование за одну и ту же дату, делая операцию голосования идемпотентной. Сущность **Message** хранит сообщение чата: `event` (FK → Event, CASCADE), `participant` (FK → Participant, SET_NULL, nullable), `text`, `created_at`. Nullable-связь с участником сделана намеренно: если запись участника будет удалена, сообщение останется в истории (поле станет NULL), что сохраняет целостность переписки.

## 2.3. Проектирование REST API

API спроектировано в соответствии с принципами REST: каждый ресурс идентифицируется уникальным URL, вид операции определяется HTTP-методом, формат обмена данными — JSON. Все маршруты подключены под единым префиксом `/api/` в корневом роутере Django, что обеспечивает пространство имён и упрощает настройку прокси.

Маршруты сгруппированы в три логических раздела. Раздел управления мероприятиями включает: создание события (`POST /api/events/`), получение списка всех событий (`GET /api/events/list/`), детальный просмотр конкретного события (`GET /api/events/<uuid:id>/`), удаление события (`DELETE /api/events/<uuid:id>/delete/`). К событию привязаны три вложенных ресурса: сообщения чата (`GET/POST /api/events/<uuid:event_id>/messages/`), участники (`GET/POST /api/events/<uuid:event_id>/participants/`) и голоса (`POST /api/events/<uuid:event_id>/votes/`).

Раздел аутентификации включает три эндпоинта. Регистрация (`POST /api/auth/register/`) принимает `username`, `email`, `password`, `password2`; выполняет валидацию пароля (длина 8–24 символа, наличие заглавной, строчной буквы и спецсимвола, совпадение полей); при успехе возвращает пару JWT-токенов и объект пользователя. Вход (`POST /api/auth/login/`) принимает `username` и `password`, проверяет хэш пароля через `check_password` и возвращает аналогичную пару токенов. Обновление токена (`POST /api/auth/refresh/`) принимает `refresh`-токен и выдаёт новый `access`-токен, не требуя повторного ввода пароля.

Защищённые эндпоинты (создание события, удаление, голосование, список событий пользователя) требуют передачи `access`-токена в заголовке `Authorization: Bearer <token>`. Кастомный класс `EventUserJWTAuthentication` декодирует токен, извлекает `user_id` и возвращает соответствующий объект `EventUser`. При отсутствии или недействительности токена возвращается код 401.

Раздел пользовательских данных содержит один маршрут: `GET /api/users/<uuid:user_id>/events/`, возвращающий список мероприятий конкретного пользователя с полными вложенными данными (варианты дат, участники, сообщения). Этот эндпоинт используется главной страницей для формирования персональной ленты событий и наполнения календаря.

Коды состояния HTTP: 200 OK — успешный ответ с данными; 201 Created — ресурс создан; 400 Bad Request — ошибка валидации входных данных с описанием в теле ответа; 401 Unauthorized — токен отсутствует или недействителен; 404 Not Found — ресурс не найден.

## 2.4. Проектирование пользовательского интерфейса

Интерфейс приложения организован как набор из пяти маршрутов: главная страница `/`, страница входа и регистрации `/login`, создание мероприятия `/create`, просмотр мероприятия `/event/:id` и обработчик несуществующих адресов `/:pathMatch(.*)`. Vue Router работает в режиме `createWebHistory`, что даёт «чистые» URL без символа `#` и позволяет пользователю открывать и передавать ссылку на конкретное мероприятие напрямую.

Общая оболочка приложения определена в корневом компоненте `App.vue` и содержит навигационную панель, зону `<router-view>` для подстановки текущей страницы и подвал. Навигация адаптируется к состоянию аутентификации: авторизованным пользователям в правой части панели показывается кнопка «Выйти», неавторизованным — ссылка «Войти». На мобильных экранах текстовые ссылки заменяются иконками с использованием Tailwind-классов `hidden sm:inline` и `sm:hidden`.

Главная страница совмещает три функциональных блока. Первый — интерактивный помесячный календарь с навигацией и отметками событий на конкретных датах. Второй — персонализированный список «Мои события» с кнопками удаления, доступный только авторизованным пользователям; гостям вместо списка показывается призыв к входу. Третий — информационная секция «Как это работает» с пошаговым описанием сценария использования.

Страница мероприятия разделена на четыре функциональные зоны: заголовок с описанием и счётчиками, секция голосования за даты, встроенный чат и список участников. Ниже расположен блок с пригласительной ссылкой и кнопкой копирования. На широких экранах секция голосования и чат размещаются рядом в сетке 2:1 (классы `lg:col-span-2`), на узких — вертикально стакаются.

При проектировании соблюдён принцип адаптивной вёрстки: все шаблоны используют Tailwind-утилиты с префиксами брейкпоинтов (`sm:`, `md:`, `lg:`). Такой подход обеспечивает корректное отображение интерфейса на устройствах с разными размерами экрана без написания медиа-запросов вручную.

# 3. Разработка веб-приложения

## 3.1. Реализация серверной части

### 3.1.1. Структура серверного приложения

Серверная часть организована как стандартный Django-проект с единственным прикладным приложением `events`. Директория `backend/` содержит два Python-пакета. Первый — конфигурационный пакет `backend/` с файлами `settings.py` (настройки проекта), `urls.py` (корневой роутер), `wsgi.py` и `asgi.py` (точки входа для WSGI/ASGI-серверов). Второй — прикладное приложение `events/` с файлами `models.py`, `serializers.py`, `views.py`, `urls.py`, `admin.py` и директорией `migrations/`.

В файле настроек `settings.py` к списку `INSTALLED_APPS` добавлены два внешних приложения: `rest_framework` и `events`. Параметры базы данных задаются в разделе `DATABASES` через движок `django.db.backends.sqlite3`. Файл базы данных `mydatabase` расположен в корне серверного проекта. В `requirements.txt` присутствуют зависимости `psycopg2-binary` и `dj-database-url`, а в `settings.py` в виде закомментированного блока подготовлена альтернативная конфигурация для PostgreSQL через переменную окружения `DATABASE_URL`. Это позволит переключить хранилище данных без изменения прикладного кода — достаточно заменить конфигурационный блок и задать строку подключения.

Корневой роутер `backend/urls.py` монтирует маршруты приложения `events` под префиксом `api/`:

```python
path('api/', include('events.urls')),
```

Маршруты самого приложения определены в `events/urls.py` и используют UUID-типизированные сегменты пути (`<uuid:id>`, `<uuid:event_id>`, `<uuid:user_id>`). Это гарантирует, что Django автоматически отклонит запросы с некорректным форматом идентификатора на уровне маршрутизации, до вызова view-функции.

Эволюция схемы базы данных фиксируется пятью файлами миграций в `events/migrations/`. Первая миграция (`0001_initial.py`) создала начальный набор сущностей. Последующие скорректировали типы полей — в частности, `DateOption.date` изменён с `DateField` на `DateTimeField` (`0002_alter_dateoption_date.py`), что позволило хранить не только дату, но и время мероприятия. Миграции `0003–0005` оформили введение модели `EventUser` и рефакторинг связей.

### 3.1.2. Реализация моделей базы данных

Все шесть моделей определены в файле `events/models.py`. Модель `EventUser` не наследует от `django.contrib.auth.models.AbstractUser` или `AbstractBaseUser`, поскольку в приложении отсутствует механизм паролей. Это сознательное упрощение: `EventUser` является Plain Django Model с тремя полями — `id` (UUID, `default=uuid.uuid4`, `editable=False`), `username` (уникальное строковое поле) и `email` (уникальное email-поле). Параметры `unique=True` создают индексы в базе данных, ускоряя поиск при аутентификации, и автоматически выбрасывают `IntegrityError` при нарушении уникальности — ошибка перехватывается и обрабатывается на уровне сериализаторов.

Модель `Event` связана с `EventUser` через `ForeignKey` с `on_delete=models.CASCADE` и именованным обратным менеджером `related_name='events'`. Именованный `related_name` позволяет обращаться к мероприятиям пользователя через `user.events.all()` без необходимости делать отдельный запрос. Аналогичный подход с `related_name` применяется для `DateOption`, `Participant`, `Message`, `Vote`: это делает ORM-запросы декларативными и позволяет DRF-сериализаторам автоматически разрешать вложенные данные.

Модели `Participant` и `Vote` используют ограничение `unique_together` для реализации бизнес-правил непосредственно на уровне схемы базы данных. В `Participant` ограничение `('event', 'event_user')` предотвращает дублирование участника в рамках одного мероприятия. В `Vote` ограничение `('participant', 'date_option')` гарантирует, что участник не проголосует за одну дату дважды. Размещение этих ограничений в базе данных, а не только в логике приложения, обеспечивает их соблюдение даже при параллельных запросах или прямых операциях с базой.

Модель `Message` использует `on_delete=models.SET_NULL` для связи с `Participant` (поле объявлено с `null=True, blank=True`). Это решение продиктовано соображениями целостности данных: если участник покинул мероприятие или его запись была удалена, история переписки должна сохраниться. В результате удаления участника поле `participant` в его сообщениях устанавливается в NULL, но сами сообщения остаются в базе. Поле `text` хранится как `TextField` без ограничения длины, что допускает произвольно длинные сообщения.

### 3.1.3. Реализация REST API

Все представления реализованы с использованием обобщённых классов Django REST Framework из модуля `rest_framework.generics`. Использование Generic Views позволяет описывать поведение эндпоинта декларативно — через атрибуты `queryset` и `serializer_class` — тогда как стандартная последовательность операций (десериализация запроса, валидация, сохранение, формирование ответа) выполняется базовым классом автоматически.

`EventCreateView` наследует `generics.CreateAPIView` и обрабатывает `POST /api/events/`. `EventDetailView` наследует `generics.RetrieveAPIView` и переопределяет атрибут `lookup_field = 'id'`: Django REST Framework по умолчанию ищет объект по полю `pk`, однако первичный ключ в модели `Event` назван `id` и является UUID, поэтому явное указание поля поиска устраняет потенциальную путаницу. `EventDeleteView` наследует `generics.DestroyAPIView` с тем же `lookup_field = 'id'` и обрабатывает `DELETE`-запросы.

`EventListView` наследует `generics.ListAPIView` и переопределяет метод `get_queryset()`. Вместо прямого `Event.objects.all()` используется `Event.objects.select_related('event_user').order_by('-created_at')`. Директива `select_related` генерирует SQL-запрос с JOIN и подгружает связанный объект `EventUser` вместе с событием за один запрос к базе, предотвращая проблему N+1 при обходе списка.

`EventMessagesView` и `EventParticipantView` наследуют `generics.ListCreateAPIView`, объединяя в одном классе поддержку `GET` (список) и `POST` (создание). Оба класса переопределяют метод `perform_create()`, добавляя `event_id` из параметра URL при сохранении объекта: `serializer.save(event_id=event_id)`. Это связывает новое сообщение или участника с правильным мероприятием, не требуя передачи `event_id` в теле запроса от клиента.

`VoteCreateView` переопределяет метод `create()` и применяет `Vote.objects.update_or_create(participant=..., date_option=...)` вместо стандартного `serializer.save()`. Это делает операцию голосования идемпотентной: если запись с такой парой `(participant, date_option)` уже существует, она будет возвращена без создания дубликата; если нет — создана. При успехе view возвращает `{'status': 'voted'}` с кодом 200 вместо 201, сигнализируя, что ресурс мог как создан, так и обновлён.

Сериализаторы определены в файле `events/serializers.py`. `EventCreateSerializer` использует кастомное поле `dates = ListField(child=DateTimeField(), write_only=True)` для приёма массива дат и переопределяет `create()`, где вызывается `DateOption.objects.bulk_create([...])` — пакетная вставка вариантов дат одним SQL-запросом вместо N отдельных `INSERT`. `EventDetailSerializer` применяет вложенные сериализаторы `DateOptionSerializer`, `ParticipantSerializer`, `MessageSerializer` с параметром `many=True, read_only=True`, формируя единый JSON-ответ с полным состоянием мероприятия.

### 3.1.4. Система аутентификации пользователей

Аутентификация реализована на основе JWT (JSON Web Token) с хэшированием паролей. Модель `EventUser` не наследует от `AbstractUser` — это Plain Django Model, дополненная тремя полями: `password` (хэш PBKDF2, `CharField(max_length=128)`), `role` (`CharField` с выбором `user`/`admin`) и `created_at` (`DateTimeField(auto_now_add=True)`). Намеренный отказ от `AbstractUser` позволяет не тянуть механизмы сессий, групп и прав Django, которые в данном приложении не используются. Свойство `is_authenticated = True` объявлено на уровне класса, что обеспечивает совместимость с механизмом проверки прав DRF без наследования от `AbstractBaseUser`.

Регистрация обрабатывается через `EventUserRegisterSerializer`. Поле `password` проходит три проверки в методе `validate_password()`: наличие заглавной буквы (`re.search(r'[A-Z]', value)`), строчной и специального символа. В методе `validate()` проверяется совпадение `password` и `password2`, уникальность `email` и `username` через `EventUser.objects.filter(...).exists()`. Перед записью пароль хэшируется вызовом `make_password(attrs['password'])` из `django.contrib.auth.hashers` — функция применяет алгоритм PBKDF2-SHA256 с солью. Сохранение выполняется через `EventUser.objects.create(**validated_data)`.

Вход обрабатывается через `EventUserLoginSerializer`. В методе `validate()` выполняется поиск пользователя по `username` и проверка пароля функцией `check_password(password, user.password)`. Логика разделена между сериализатором и view намеренно: сериализатор отвечает за проверку данных, view — за формирование ответа.

После успешной регистрации или входа вспомогательная функция `make_jwt_pair(user)` формирует пару токенов через `rest_framework_simplejwt`. В `RefreshToken` вручную записываются поля `user_id`, `username` и `role` — это позволяет идентифицировать пользователя из токена без обращения к базе данных при каждом запросе. Время жизни: `access` — 60 минут, `refresh` — 7 дней. Оба токена возвращаются клиенту вместе с объектом пользователя.

Проверка токена на защищённых эндпоинтах выполняется классом `EventUserJWTAuthentication(BaseAuthentication)`. Метод `authenticate()` читает заголовок `Authorization: Bearer <token>`, декодирует `access`-токен через `AccessToken(token_str)`, извлекает `user_id` и возвращает кортеж `(user, token)`. Если токен повреждён или истёк — поднимается `AuthenticationFailed` (401). Метод `authenticate_header()` возвращает строку `'Bearer realm="api"'`, что заставляет DRF корректно возвращать статус 401 вместо 403 при неаутентифицированном запросе — это важно для корректной работы axios-перехватчика на клиенте.

Клиентская сторона хранит `access_token` и `refresh_token` в `localStorage`. Axios request interceptor автоматически добавляет `Authorization: Bearer <access>` ко всем запросам. Response interceptor перехватывает 401: пробует обновить токен через `POST /api/auth/refresh/`; при неудаче очищает `localStorage` и перенаправляет на `/login`.

### 3.1.5. Бизнес-логика создания событий и голосования

Создание мероприятия представляет собой атомарную операцию, затрагивающую две связанные таблицы: `events_event` и `events_dateoption`. Эта логика инкапсулирована в методе `create()` класса `EventCreateSerializer`, чтобы view оставался максимально простым. Поле `dates` в сериализаторе объявлено с параметром `write_only=True`: оно принимается во входных данных запроса, но не сериализуется обратно в ответ. Это позволяет фронтенду передавать удобный список дат и получить в ответ стандартное представление созданного события.

В методе `create()` список дат извлекается из `validated_data` через `pop('dates')`, после чего создаётся объект `Event`. Затем используется `DateOption.objects.bulk_create([DateOption(event=event, date=date) for date in dates])`. Пакетная вставка (`bulk_create`) генерирует единственный SQL-запрос `INSERT ... VALUES (...), (...), (...)` вместо N отдельных запросов, что ускоряет операцию пропорционально числу вариантов дат.

Логика голосования реализована в `VoteCreateView.create()`. Метод `Vote.objects.update_or_create(participant=..., date_option=...)` обращается к базе данных с семантикой UPSERT: если запись существует — вернуть её, если нет — создать. Такой подход устойчив к дублирующимся запросам от клиента (например, при повторной отправке формы из-за задержки сети) и корректно обрабатывает смену голоса участника.

Для получения списка мероприятий пользователя `UserEventsView` применяет `prefetch_related('date_options', 'participants', 'messages')`. Django ORM выполняет для каждого из трёх связанных наборов отдельный запрос с условием `WHERE event_id IN (...)`, собирает результаты в Python и привязывает их к соответствующим объектам `Event`. Альтернатива — обращение к связанным объектам внутри сериализатора без prefetch — привела бы к проблеме N+1: при 20 событиях было бы выполнено 60 дополнительных запросов вместо 3.

### 3.2.1. Структура клиентского приложения

Клиентское приложение собирается инструментом Vite 7.3 с плагином `@vitejs/plugin-vue`. Точка входа — файл `src/main.js`, в котором создаётся экземпляр Vue-приложения через `createApp(App)`, регистрируются плагины `createPinia()` и `router`, а затем вызывается `authStore.initializeFromStorage()`. Этот вызов до `app.mount('#app')` гарантирует, что при перезагрузке страницы состояние аутентификации будет восстановлено из `localStorage` прежде, чем любой компонент начнёт рендериться. Без этого пользователь на долю секунды видел бы интерфейс «неавторизованного» состояния перед появлением данных.

В файле `vite.config.js` задан псевдоним `@` для директории `src` — `path.resolve(__dirname, './src')`. Это позволяет использовать абсолютные пути вида `@/stores/auth` вместо относительных `../../stores/auth`, что упрощает рефакторинг и перемещение файлов. Там же настроен proxy-сервер: все запросы на `/api` перенаправляются к `http://127.0.0.1:8000` (Django) с параметром `changeOrigin: true`, обеспечивающим корректную подмену заголовка `Host`.

Tailwind CSS настроен через `tailwind.config.js` с параметром `content`, указывающим на HTML-шаблоны Vue-компонентов. PostCSS-плагин `@tailwindcss/postcss` встраивается в pipeline Vite и генерирует финальный CSS только из тех утилитарных классов, которые реально используются в коде. Это позволяет держать размер CSS-бандла минимальным.

Структура директории `src/` разделена на четыре каталога: `views/` (страницы, подключаемые роутером), `components/` (переиспользуемые компоненты), `stores/` (Pinia-хранилища) и `api/` (конфигурация HTTP-клиента). Такое разделение соответствует принципу разделения ответственности и является стандартной конвенцией для Vue-проектов.

### 3.2.2. Управление состоянием приложения

Управление состоянием реализовано через Pinia 3.0 — официальный менеджер состояния для Vue 3. В отличие от Vuex, Pinia не требует объявления мутаций и модулей: каждое хранилище определяется функцией `defineStore()` с прямым объявлением `state`, `actions` и `getters`. Vue DevTools автоматически интегрируется с Pinia и отображает текущее состояние всех хранилищ в панели разработчика.

Хранилище `useAuthStore` (`stores/auth.js`) хранит объект текущего пользователя в поле `user` (начальное значение `null`). Геттер `isAuthenticated` возвращает `!!state.user` — булев флаг, который шаблоны компонентов используют в директивах `v-if` для условного рендеринга. Геттер `userId` возвращает `state.user?.id || null`. Action `login()` вызывает `api.post('/auth/login/', payload)` и при успехе передаёт ответ в `setUser()`, который одновременно записывает данные в реактивное состояние и в `localStorage`. Action `logout()` обнуляет `user` и удаляет запись из `localStorage`.

Вспомогательный метод `extractAuthError()` в `useAuthStore` нормализует разнородные форматы ошибок, которые Django REST Framework возвращает в зависимости от типа проблемы. DRF может вернуть объект с именами полей (`{'email': ['...'], 'username': ['...']}`) для ошибок валидации, поле `detail` для общих ошибок, простую строку или массив строк. Метод проверяет поочерёдно: `error?.response?.data?.username?.[0]`, `error?.response?.data?.email?.[0]`, `error?.response?.data?.detail`, `error?.message` и возвращает первое найденное строковое значение.

Хранилище `useEventStore` (`stores/event.js`) управляет состоянием текущего открытого мероприятия. Action `createEvent()` реализует двухуровневый механизм: в первую очередь отправляется запрос к Django API; при недоступности сервера (перехваченная ошибка Axios) создаётся локальный объект с временным идентификатором `evt_local_<timestamp>` и сохраняется в `localStorage`. Это «деградирующее» поведение позволяет приложению работать даже при временных сбоях соединения. Геттер `votesByDate` агрегирует голоса через `reduce()`, формируя словарь `{ dateString: [voterName, ...] }`, который используется компонентом голосования для отображения прогресс-баров.

### 3.2.3. Реализация страниц и компонентов

### 3.2.4. Взаимодействие с серверным API

Все HTTP-запросы к серверу осуществляются через единственный экземпляр Axios, создаваемый в файле `src/api/index.js`. Экземпляр настроен с `baseURL: '/api'`, что соответствует пути, проксируемому Vite на Django. Заголовки `Content-Type: application/json` и `Accept: application/json` гарантируют, что Django REST Framework вернёт данные в JSON-формате, а не в HTML (Browsable API). Параметр `timeout: 5000` (5 секунд) предотвращает бесконечное ожидание при медленном соединении.

На экземпляре зарегистрирован перехватчик ответов через `api.interceptors.response.use()`. При успешном ответе (2xx) данные проходят без изменений. При ошибке перехватчик извлекает понятное сообщение из тела ответа Django, проверяя три возможных формата: поле `detail` (стандартная DRF-ошибка), простая строка, массив строк. Нормализованное сообщение записывается в `error.message`, после чего ошибка повторно поднимается через `Promise.reject(error)`. Это позволяет хранилищам Pinia обрабатывать ошибки единообразно, не разбираясь в структуре ответа сервера.

Axios-экземпляр экспортируется как именованный (`export { api }`) и как дефолтный (`export default api`), что позволяет использовать оба варианта импорта в компонентах и хранилищах в зависимости от стиля кода. В хранилищах вызовы к API выполняются в методах actions: `api.post('/auth/login/', payload)`, `api.get('/users/<id>/events/')`, `api.delete('/events/<id>/delete/')` и другие. Результаты сохраняются в реактивное состояние, что автоматически вызывает перерендер зависящих компонентов.

Проксирование настроено в секции `server.proxy` файла `vite.config.js`. Правило `'/api': { target: 'http://127.0.0.1:8000', changeOrigin: true }` перенаправляет запросы к `/api/...` на `http://127.0.0.1:8000/api/...`. Параметр `changeOrigin: true` означает, что Vite подставляет в заголовок `Host` адрес целевого сервера (Django), а не адрес браузера. Такая схема устраняет необходимость настраивать CORS-заголовки на стороне Django при разработке.

## 3.3. Интеграция клиентской и серверной частей

Взаимодействие клиентской и серверной частей организовано через HTTP REST API с JSON в качестве формата обмена данными. При разработке Vite proxy выступает посредником: браузер отправляет запросы к `localhost:5173/api/...`, Vite их получает и без каких-либо изменений в теле перенаправляет к `localhost:8000/api/...`. С точки зрения Django, запрос поступает от Vite как от обычного HTTP-клиента. Это позволяет запускать оба сервера независимо без дополнительной конфигурации.

Аутентификационный контекст передаётся через JWT-токен в заголовке `Authorization: Bearer <token>`. При создании мероприятия клиент включает UUID из `authStore.userId` в поле `event_user` тела запроса; сервер дополнительно верифицирует токен через `EventUserJWTAuthentication` и отклоняет запрос с кодом 401, если токен отсутствует или недействителен. Такая двойная проверка — через тело запроса и через заголовок — обеспечивает целостность данных.

При монтировании `App.vue` в `main.js` вызывается `authStore.initializeFromStorage()`, который читает ранее сохранённые данные пользователя из `localStorage`. Это обеспечивает сохранение сессии между перезагрузками страницы без обращения к серверу. Данные в `localStorage` хранятся под ключом `'user'` как JSON-строка объекта `{id, username, email}`.

Для операции удаления мероприятия применена «пессимистичная» стратегия обновления UI: сначала выполняется `api.delete('/events/<id>/delete/')`, и только после получения успешного ответа (без ошибок) список событий перезагружается через `loadUserCalendarEvents()`. Такой порядок гарантирует, что UI всегда отражает реальное состояние базы данных, а не оптимистичный прогноз. При ошибке удаления в компоненте отображается сообщение `eventsError`, не изменяя список.

# Приложение А. Краткое описание реализованного функционала
## (для слайда на предзащите)

1. **Регистрация и аутентификация пользователей.** Пользователь регистрируется по имени, email и паролю. Пароль хэшируется алгоритмом PBKDF2-SHA256. После регистрации или входа сервер возвращает пару JWT-токенов (access — 60 мин, refresh — 7 дней). Токены хранятся в `localStorage`; при истечении access-токена клиент автоматически запрашивает новый по refresh-токену без повторного входа.

2. **Создание совместных мероприятий.** Авторизованный пользователь заполняет форму с названием, описанием и несколькими вариантами дат. Все данные атомарно сохраняются на сервере: событие и связанные варианты дат — за один HTTP-запрос.

3. **Голосование за удобные даты.** Участники мероприятия выбирают подходящие даты из предложенных вариантов. Голосование идемпотентно: повторный запрос не создаёт дубликат. Для каждой даты отображается прогресс-бар с числом голосов и списком проголосовавших.

4. **Автоматическое определение лучшей даты.** Компонент голосования `VotePanel.vue` сортирует варианты по убыванию числа голосов и выделяет победителя в отдельном блоке «Наиболее удобная дата».

5. **Интерактивный персональный календарь.** Главная страница отображает помесячный календарь с отметками на датах мероприятий текущего пользователя. Клик по дате показывает список событий на этот день в боковой панели.

6. **Управление событиями.** Создатель мероприятия видит список своих событий с датами создания, ссылками для открытия и кнопками удаления. Удаление выполняется с подтверждением и немедленно обновляет список.

7. **Чат мероприятия.** На странице мероприятия встроен компонент чата для обмена сообщениями между участниками в контексте конкретного события.

8. **Пригласительная ссылка.** Каждому мероприятию автоматически соответствует уникальный URL на основе UUID. Ссылку можно скопировать в буфер обмена одним кликом и отправить участникам.
