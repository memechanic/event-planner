# Отчет о доработках системы планирования событий (формат ВКР)

## 1. Цель работы

Целью выполненных доработок являлось развитие веб-приложения планирования событий в части:
- пользовательской авторизации;
- управления пользовательскими событиями;
- повышения удобства взаимодействия с календарным интерфейсом;
- улучшения прозрачности ошибок и надежности клиент-серверного взаимодействия.

Основной целевой результат: обеспечить разделение сценариев входа и регистрации, добавить управление списком событий пользователя (просмотр и удаление), а также интегрировать календарный интерфейс с актуальными данными backend.

---

## 2. Задачи, решенные в ходе работы

В рамках достижения цели были поставлены и решены следующие задачи:

1. Проанализировать существующую реализацию авторизации и выявить смешение сценариев входа и регистрации.
2. Реализовать раздельные backend-endpoint’ы для регистрации и входа пользователя.
3. Ввести серверную валидацию:
   - проверку уникальности пользователя при регистрации;
   - проверку существования пользователя и корректности пары `email + username` при входе.
4. Адаптировать frontend-логику авторизации под раздельные сценарии.
5. Добавить в интерфейс отдельные элементы управления для действий «Войти» и «Зарегистрироваться».
6. Интегрировать функционал списка пользовательских событий на главной странице.
7. Реализовать удаление событий пользователя с последующим обновлением интерфейса.
8. Улучшить календарный интерфейс (переход к текущей дате, отображение реальных данных событий).

---

## 3. Архитектурные решения

## 3.1. Архитектура backend

Backend реализован на Django + Django REST Framework. Для API применены стандартные классы `rest_framework.generics`, что обеспечивает:
- единообразие реализации endpoint’ов;
- минимизацию шаблонного кода;
- предсказуемость жизненного цикла запроса.

Использованные классы:
- `CreateAPIView` — создание сущностей (регистрация пользователя, создание события);
- `ListAPIView` — выдача списков (список событий);
- `DestroyAPIView` — удаление сущностей (удаление события);
- `GenericAPIView` — кастомная логика входа пользователя при сохранении DRF-подхода к валидации.

Ключевое решение: вынести бизнес-валидацию входа/регистрации в сериализаторы, чтобы централизовать правила и сохранить тонкий контроллерный слой (`views`).

## 3.2. Архитектура frontend

Frontend реализован на Vue 3 c Pinia и Axios.

Принятые решения:
- централизация авторизационной логики в `auth` store;
- разделение действий авторизации на отдельные методы (`login`, `register`);
- стандартизированная обработка API-ошибок в store с передачей человекочитаемых сообщений в UI;
- реактивное обновление календаря и списка событий после операций загрузки и удаления.

Ключевое решение: не смешивать сетевую логику с шаблоном представления (`LoginView`), а использовать store как единый слой состояния и доступа к API.

## 4. Реализованные изменения

## 4.1. Изменения на backend

1. **Разделение авторизации**
   - Добавлен endpoint регистрации:
     - `POST /api/auth/register/`
   - Добавлен endpoint входа:
     - `POST /api/auth/login/`

2. **Серверная валидация пользователя**
   - При регистрации:
     - отклонение запроса при существующем `email`;
     - отклонение запроса при занятом `username`.
   - При входе:
     - проверка существования пользователя по `email`;
     - проверка соответствия `username` указанному `email`.

3. **Операции с событиями**
   - Добавлен endpoint списка событий:
     - `GET /api/events/list/`
   - Добавлен endpoint удаления события:
     - `DELETE /api/events/<uuid:id>/delete/`
   - Использованы базовые DRF generic-классы.

## 4.2. Изменения на frontend

1. **Разделение сценариев входа и регистрации**
   - На форме добавлены отдельные кнопки:
     - «Войти»;
     - «Зарегистрироваться».
   - Для каждого действия используется отдельный метод store.

2. **Улучшение UX авторизации**
   - Добавлена валидация обязательных полей до отправки запроса;
   - Добавлен вывод понятных сообщений об ошибке от backend.

3. **Развитие интерфейса календаря**
   - Подключение календаря к реальным данным пользователя;
   - Добавление кнопки перехода к текущей дате;
   - Добавление блока «Мои события»:
     - отображение списка событий пользователя;
     - удаление события из интерфейса;
     - автоматическое обновление списка и календаря после удаления.

## 5. Использованные способы и технологии

- **Язык и фреймворки:** Python (Django, DRF), JavaScript (Vue 3).
- **Управление состоянием:** Pinia.
- **HTTP-клиент:** Axios.
- **Проектирование API:** REST-подход с выделенными endpoint’ами для CRUD/аутентификации.
- **Валидация:**
  - backend: сериализаторы DRF (`validate`);
  - frontend: проверка обязательных полей + отображение серверных ошибок.
- **Паттерн интеграции:** frontend как потребитель API с реактивным обновлением представления по результатам операций.
